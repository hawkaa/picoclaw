## Patterns That Work
- Telegram typing indicator: send `sendChatAction` every 4s while container is active; stop on agent output. No way to cancel explicitly — indicator expires in ~5s naturally.
- Container tracking is in-memory only — on restart, orphaned containers must be stopped via `docker stop`. Implemented `cleanupOrphanedContainers()` called at startup.
- **[2026-06-28] Deploy host-side changes**: deploy checkout is `/root/.picoclaw` on branch `main`; `systemctl restart picoclaw` (systemd unit `picoclaw.service`). Host runs `bun run src/index.ts` with no `--watch`, so a restart is required to pick up `src/*.ts` edits; startup auto-runs `cleanupOrphanedContainers()`. Changes under `container/agent-runner` additionally need the image rebuilt (`bash container/build.sh`).
- **[2026-07-09, rev 2026-07-19] Pull + restart flow**: `config.ts` carries the uncommitted `WORKSPACES_DIR` override, so `git stash push -- src/config.ts` → `git pull --ff-only` → `git stash pop` (clean pop verified through PR #30's config.ts rewrite). If a `docker ps --filter name=picoclaw-` container exists, check `journalctl -u picoclaw` for the last `Result #N: stop_reason=end_turn` — idle post-end_turn means the reply is already delivered and restart is safe; only a query in flight gets cut off (IDLE/CONTAINER_TIMEOUT are both 60 min, so idle containers linger — don't wait them out). Verify after: `systemctl is-active picoclaw`, empty `docker ps --filter name=picoclaw-`, journal shows "IPC watcher started" + "Task scheduler started".
- **[2026-09-08, fixed 2026-09-26] A base-image bump used to NOT reach per-chat images**: `resolveImage()` keyed `picoclaw-<chat>:latest` on `Dockerfile.extra` alone, so `container/build.sh` left chats on old base layers (Sep 8 workaround was a manual rebuild; it recurred Sep 24–26 as `claude_code_version_too_old` on every opus turn). Now the key in `data/image-hashes.json` is sha256(base image ID + extra), so the next spawn after a base rebuild rebuilds the chat image (~4–5 min for 6636146019). No manual step needed.
- **[2026-09-08] Preconditions need bun on the SERVICE PATH — silent-skip trap**: `preconditions/*` are `#!/usr/bin/env bun` scripts and systemd's default PATH (`/usr/local/sbin:...:/snap/bin`) has no `/root/.bun/bin`, while the unit invokes bun by absolute path so nothing else notices. `env` then exits **127**, which `precondition.ts` reads as a legal `1..254` "not-met" → `shouldSpawn:false`, i.e. the cron dies silently and permanently — the exact failure the fail-open design was written to prevent, delivered through the one code path that bypasses it. Fixed with drop-in `/etc/systemd/system/picoclaw.service.d/path.conf` setting `Environment=PATH=/root/.bun/bin:...`. Do instead: after touching the unit or moving bun, re-prove it — a check that returns "not-met" for EVERY input looks identical to a working check that says "no work".
- **[2026-07-19] Provider API keys (PR #30 routing)**: host env via systemd `EnvironmentFile=/root/.picoclaw/.env` — `OPENROUTER_API_KEY` (any `vendor/model` id), `MOONSHOT_API_KEY` (kimi aliases). Read from `process.env` at container spawn (`container-runner.ts`), so adding/rotating a key needs `systemctl restart picoclaw`. Validate a key without spawning: `curl https://openrouter.ai/api/v1/key -H "Authorization: Bearer $KEY"` → 200.
- **[2026-07-19] Open a PR to hawkaa/picoclaw from this host** (no `gh` CLI): hawkaa's stored PAT (`~/.git-credentials`, helper=store) pushes branches but 403s on the PR API (`pull_requests: write` missing). Working flow: push the branch to the fork `piiiico/picoclaw` with Pico's `ghp_` token (grep a `.git/config` under workspace `memory/play/*`), then POST `/repos/hawkaa/picoclaw/pulls` with `head: "piiiico:<branch>"` using that token (direct-branch head → 422 "must be a collaborator"). CRITICAL: an inline-token push gets appended to `~/.git-credentials` as `x-access-token:...` and SHADOWS hawkaa's entry for all of github.com — grep -v it back out afterwards or the deploy pull flow breaks.
- Typing should be turn-based: start on container spawn or follow-up message, stop on any `handleOutput` call (null result or not).
- **[2026-07-18] Create a one-off scheduled task**: append to `data/tasks.json` — `schedule_type:"once"`, `next_run` SET to the fire ISO (fires when `status:"active" && next_run<=now`; auto-pauses after, `computeNextRun` returns null for once). Scheduler tick 60s, max 3 concurrent spawns, no restart.
